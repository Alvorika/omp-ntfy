# omp-ntfy

> Web Push notifications when an Oh My Pi (OMP) agent finishes a task.
> [GitHub](https://github.com/Alvorika/omp-ntfy) · [Changelog](CHANGELOG.md) · MIT License

> **Experimental.** This is v0.1.0 of a personal single-user tool. The
> CLI, HTTP endpoints, and config format may change between versions;
> not recommended for multi-user or production environments.

Get a Web Push notification on your Mac/iPhone when an Oh My Pi (OMP)
agent finishes a task on a remote machine.

```
OMP agent (remote box)
  │  OMP extension (official event API, no OMP internals touched)
  │  POST /api/events  (Bearer token, 3s timeout, failures swallowed)
  ▼
omp-ntfy server (single static binary, systemd user service or container)
  │  RFC 8030 + RFC 8291: VAPID-signed, aes128gcm-encrypted Web Push
  ▼
PWA / Service Worker  →  macOS / iPhone notification
```

Single-user, self-hosted, deliberately small. v0 scope: notify on task
completion only. No replay, no plan/tool approval, no remote control,
no chat UI, no user accounts.

## What fires a notification

The extension listens for the official `session_stop` extension event —
OMP's main-session stop hook. Why this event:

- OMP never emits it for task/subagent sessions (enforced in the runner),
  so subagents can never cause duplicate notifications.
- It fires **once** when the session settles, not per turn, so
  intermediate turns don't spam you.
- It is not emitted for aborted sessions (Escape / cancelled), so you
  don't get "completed" pings for work that was stopped.
- `turn_end` / `agent_end` are intentionally unused.

Typical usage: `omp -p "long task"` on the remote box; when the process
exists, your devices buzz. Interactive sessions notify when the session
settles.

Notification payload is metadata only — session name, cwd basename,
duration. Never prompts, tool arguments, commands, or message content.

## Build

```sh
cargo build --release
install -m755 target/release/omp-ntfy ~/.local/bin/omp-ntfy
```

Requires a Rust toolchain (1.97+, edition 2024) only at build time; the
binary has zero runtime dependencies. No root needed anywhere.

Release artifacts are built by `scripts/build-release.sh` (tarball + sha256,
glibc per default; `--musl` for a fully static binary).

## 1. Run the server (native)

```sh
omp-ntfy init                                   # one-time: creates config + VAPID keys
omp-ntfy serve                                  # foreground, http://127.0.0.1:8090
```

As a systemd **user** service (no root):

```sh
omp-ntfy service install      # write unit, enable --now
omp-ntfy service status       # systemctl --user status
omp-ntfy service start|stop|restart
omp-ntfy service uninstall    # stop, disable, remove unit
```

Paths (XDG):

| Thing | Path |
|---|---|
| config (token, VAPID private key) | `$XDG_CONFIG_HOME/omp-ntfy/config.json` |
| state (subscriptions, event log) | `$XDG_STATE_HOME/omp-ntfy/store.json` |
| OMP extension client config | `$XDG_CONFIG_HOME/omp-ntfy/client.json` |

### Docker (optional alternative — same binary, same config)

```sh
OMP_NTFY_TOKEN=secret docker compose up -d --build
```

- Runs the exact same `omp-ntfy serve`; config via identical env vars.
- `OMP_NTFY_TOKEN` is required (first boot also generates VAPID keys).
- The subscription database persists in the `omp-ntfy-data` volume.

## 2. Configuration

Everything is env-overridable, so native and Docker use one surface:

| Env | Default | Used by |
|---|---|---|
| `OMP_NTFY_BIND` | `127.0.0.1:8090` | server listen address |
| `OMP_NTFY_TOKEN` | random (from `init`) | OMP → server bearer token |
| `OMP_NTFY_SUBJECT` | `mailto:omp-ntfy@localhost` | VAPID subject (use `mailto:you@…`) |
| `OMP_NTFY_CONFIG_DIR` | `~/.config/omp-ntfy` | config + client files |
| `OMP_NTFY_DATA_DIR` | `~/.local/state/omp-ntfy` | store.json |
| `OMP_NTFY_URL` / `OMP_NTFY_TOKEN` | — | extension endpoint/token (client) |
| `OMP_NTFY_CONFIG` | — | extension: explicit client config path |

VAPID keys: generated by `init`; the private key lives only in the
server config. The PWA receives only the **public** key (safe by design
— it is included in every push). No secrets are embedded in the bundle.

Manage devices and tokens:

```sh
omp-ntfy subs          # list subscribed devices
omp-ntfy subs-rm 0     # remove by index
omp-ntfy token         # show bearer token
omp-ntfy token-rotate  # rotate it (update client configs afterwards!)
omp-ntfy push-test     # send a test notification to all devices
```

## 3. Install / subscribe the PWA

Open the server through HTTPS on the device you want to subscribe.
`localhost` may be used for local development only — browsers require a
secure context (HTTPS or localhost) for Web Push.

- **Desktop (Chrome/Edge):** the page prompts for notification
  permission → click **Enable + subscribe**. Optionally "Install app"
  from the address bar for a standalone window.
- **macOS Safari 16.4+:** open the site in Safari and subscribe —
  Web Push is available directly from the web page, no Home Screen
  install required.
- **iOS/iPadOS 16.4+:** Web Push requires a Home Screen web app: in
  Safari tap **Share → Add to Home Screen**, open the installed app,
  then subscribe (Home Screen install is a hard iOS requirement).

The status card shows: server reachability, permission state, and
whether this device is subscribed. "Device name" is stored locally and
sent with the subscription for `omp-ntfy subs`.

## 4. Install the OMP extension (per machine)

On every machine that runs OMP (the remote box(es)):

```sh
omp-ntfy omp install --url <server-url> --token <server-token>
omp-ntfy omp status     # show what is installed where
omp-ntfy omp update     # re-copy after upgrading omp-ntfy
omp-ntfy omp uninstall  # remove the extension (client config kept)
```

This copies a single `<150-line` TypeScript file into
`~/.omp/agent/extensions/omp-ntfy.ts` — OMP's auto-discovered user
extension directory. No OMP config files or internals are modified, and
nothing is run as root. The extension reads `~/.config/omp-ntfy/client.json`
(or `OMP_NTFY_URL`/`OMP_NTFY_TOKEN`) and is otherwise stateless: it knows
nothing about subscriptions or the PWA.

Profile support: `--profile <name>` installs into
`~/.omp/profiles/<name>/agent/extensions`; `--agent-dir <path>` overrides
anything (`PI_CODING_AGENT_DIR` is honored too).

## 5. Security model (v0)

- OMP → server: HTTPS (or Tailscale) + `Authorization: Bearer <token>`,
  constant-time comparison, strict JSON validation, 16 KiB body limit.
- Server → push services: VAPID (ES256) signed with the private key;
  payload encrypted with RFC 8291 (aes128gcm) so push services only see
  ciphertext.
- No secrets in the PWA bundle; subscription endpoints are the only
  PWA → server writes and are authenticated by network boundary.
- Dead subscriptions (404/410) are pruned automatically.
- Extension: 3-second timeout; network failures are logged and never
  affect the OMP session.

## 6. End-to-end test procedure

Boundary (no device needed):

```sh
# 1. crypto: byte-exact against the RFC 8291 Appendix A vector
cargo test

# 2. push delivery to a fake push service
python3 tools/fake-push-endpoint.py 9123 &
omp-ntfy push-test --url http://127.0.0.1:8090   # after adding a sub like:
curl -X POST http://127.0.0.1:8090/api/subscribe -H 'content-type: application/json' \
  -d '{"endpoint":"http://127.0.0.1:9123/push/x","keys":{"p256dh":"<65B b64url>","auth":"<16B b64url>"}}'
# the fake endpoint's stdout shows authorization: vapid t=…k=…, content-encoding: aes128gcm
```

Full acceptance (the success criterion):

1. `omp-ntfy service install` — server reachable at `https://<host>/healthz`
   (locally: `http://127.0.0.1:8090/healthz`).
2. Open the PWA, subscribe (this machine's Chrome pushes through FCM).
3. `omp-ntfy omp install --url https://<host> --token …` on the remote box.
4. Start a task, leave the terminal:
   `omp -p "deploy staging"`.
5. Mac/iPhone notification: `OMP · <session|dir> — Task completed · 12m`.
6. Kill the server, re-run — OMP finishes normally, no crash, log line
   `[omp-ntfy] notification failed: …` in `~/.omp/logs`.

## Out of scope (later)

Reply-from-phone, plan approval, tool approval, remote session control,
terminal streaming, chat UI, user accounts, multi-user, dashboards. The
extension already emits only `session_stop`; adding `turn_end`-based
progress later is a server-side + extension-side option, not an
architecture change. Messages flow one way by design — nothing
server-side can address the OMP session yet.
